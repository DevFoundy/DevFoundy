Your First Version Probably Needs Less

One useful task, from beginning to end. That’s a good place to start.

By Kenta·November 2, 2026·3 min read

A new project can grow very quickly before you’ve built anything.

You start with a useful idea. Then you think of a dashboard, saved preferences, notifications, sharing, and a settings page for features that don’t exist yet.

Every addition sounds reasonable. Together, they make it harder to answer a basic question:

What should someone be able to finish in the first version?

That’s the question I want to keep close while building DevFoundy and the projects around it.

Describe one complete task

“Build a workout app” leaves a lot of room for interpretation. “Let someone record a workout and find it again” gives you a more concrete starting point.

The same approach works for a portfolio. Instead of planning every possible page, start with what a visitor needs: understand the work, see a relevant example, and find a way to get in touch.

Write that task in one sentence. If the sentence needs several “and also” clauses, try making it smaller.

This doesn’t decide the whole future of the project. It gives the first version a finish line.

Small still needs to work

A smaller scope should make room to finish the details that belong to the main task.

If someone can save an item, can they tell that it saved? If there are no items yet, does the page explain what to do? If something fails, is there a useful next step?

Those details are part of completing the task. They deserve attention before adding another feature.

For a simple contact page, that might mean checking the email link, making the text readable on a phone, and ensuring the visitor can find their way back. It’s ordinary work, but it determines whether the page is useful.

Give later ideas a place to wait

It’s hard to leave an idea out when you’re worried you’ll forget it.

A separate “later” list helps. Write down the feature and the problem it would solve. Then return to the thing you’re currently trying to finish.

Before moving an item into the first version, ask:

  • Does the main task depend on this?
  • What happens if it isn’t there?
  • Can the person still finish what they came to do?

Sometimes the answer reveals a missing essential. Sometimes it reveals a nice extra. Both are useful discoveries.

The point is to make that choice deliberately.

Try the whole journey

Once the main task works, go through it from the beginning. Use the page as someone arriving for the first time. Avoid relying on knowledge that only you have as its builder.

Read the labels. Follow the links. Try an empty state. Check a narrow screen. Look for the place where you hesitate.

That hesitation is often a better next task than the feature you were about to add.

Let the next version answer a real question

There will always be another possibility. The first version gives you something concrete to examine and share.

You can ask someone to try it. You can see which explanation they need. You can find out whether the main task is useful enough to keep improving.

I want to carry that approach into DevFoundy: choose a clear task, finish it, and learn from something people can actually use.

One complete task is a worthwhile first version.
