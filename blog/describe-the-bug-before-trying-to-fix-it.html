Describe the Bug Before Trying to Fix It

“It doesn't work” is a starting reaction. A more specific description gives me something I can investigate.

By KentaOctober 24, 20262 min read

When something in a project doesn't work, it's tempting to start changing things immediately.

There's a problem on the screen, and the obvious aim is to make it disappear.

But before choosing a fix, I think there's value in describing the problem properly.

What did I do? What did I expect? What actually happened?

Those are simple questions, but they can make a vague issue much more concrete.

The Difference Matters

Imagine pressing a save button.

“Saving is broken” could mean several things. The button might not respond. An error might appear. The page might say the save succeeded, but the result might be missing when you return.

Those experiences look related, but they point towards different questions.

I'd want to know which one I'm dealing with before deciding what to change.

Make It Possible to Repeat

A problem I can reproduce is easier to examine than one I only remember roughly.

If particular steps lead to it, writing those steps down gives me something to return to after making a change.

I can check whether the same task now behaves differently, instead of deciding that things seem better because the page opens.

That seems useful whether I'm working something out myself or asking for help.

I don't think describing a bug guarantees that I'll understand the cause. There may still be plenty of unfamiliar code to work through.

But it gives the investigation a clearer beginning.

Before I ask how to fix something, I want to be able to explain what “fixed” would actually look like.
